# Проверка EKT backend в Postman

Отдельный сценарий: [нет товара и проверка возможности замены на реальных данных](../docs/demo/README.md),
[демо-коллекция](EKT-Unavailable-Product.postman_collection.json). Включает зафиксированные незакрытые требования.

Импортируемый файл: [EKT-Backend.postman_collection.json](EKT-Backend.postman_collection.json).
Маршруты и тела взяты из контроллеров и [контракта API](../docs/frontend-api.md).
Коллекция содержит 19 запросов: дополнительные чтения позволяют проверить, что
предложение, повторное подтверждение и отказ не меняют корзину неожиданным образом.

## Подготовка

1. Запустите PostgreSQL через `docker compose up -d --wait db` из корня проекта.
2. Запустите Spring Boot из IDE по [инструкции backend](../README.md).
   `DB_URL` должен соответствовать порту контейнера, включая ваш `DB_PORT`.
3. Для свежих карточек и корзины в окружении **backend** нужны
   `EKT_ENABLED=true`, `EKT_BASE_URL`, `EKT_USERNAME`, `EKT_PASSWORD`.
   Эти доступы не нужно вводить в Postman.
4. В PostgreSQL должны быть импортированы товары с подробными карточками.
   Если каталог пуст, сначала выполните импорт по инструкции backend.
   Коллекция сама импорт не запускает.

Docker Compose читает `.env`; Spring Boot автоматически его не читает.
Передайте переменные в конфигурации запуска IDE. Секретов в коллекции нет.

## Запуск в Postman

1. **Import → Files** → выберите JSON коллекции.
2. Откройте **Variables** коллекции и задайте `baseUrl`, по умолчанию
   `http://localhost:8080`, без завершающего `/`.
3. Оставьте **No environment**, чтобы переменные окружения Postman не перекрывали
   автоматически получаемые ID и токен. При использовании своего environment
   не дублируйте в нём переменные коллекции.
4. Выберите коллекцию → **Run collection**, отметьте все запросы,
   сохраните порядок 01–19, установите **Iterations = 1** и запустите.
   Для запросов к EKT/LLM установите таймаут не меньше 45 секунд.
5. Проверьте **Passed**, **Failed** и **Skipped**. Отсутствие ошибок при наличии
   Skipped не означает, что реальные ответы LLM или аналоги были проверены.

Каждый полный запуск создаёт новую сессию и добавляет товар в её локальную
демонстрационную корзину. Заказ EKT не оформляется, складской резерв не создаётся.
Проверка ссылки `cartUrl` проверяет формат URL, а не существование страницы фронтенда.

## Переменные

| Переменная | Как используется |
|---|---|
| `baseUrl` | Адрес вашего Spring Boot |
| `productId` | Можно задать ID импортированного товара. Если пусто, выбирается товар с остатком и ценой из первых 100 записей |
| `quantity` | Можно задать количество. Если пусто, берётся `KRATNOST_MIN` из свежей карточки или 1 |
| `analogProductId` | Отдельный товар для проверки аналогов; если пусто, используется `productId` |
| `sessionId` | Автоматически сохраняется `token` из `POST /api/session`, передаётся как `Bearer`; это не UUID сессии из БД |
| `proposalId`, `proposalRevision` | Автоматически сохраняются из предложения |
| `article`, `articleEncoded` | Исходный артикул из БД и его URL-кодирование; `_` и ведущие нули не удаляются |
| `stock`, `excessQuantity` | Свежий остаток и заведомо большее количество для отрицательной проверки |
| `proposalRequestId`, `messageId1`, `messageId2` | Генерируемые UUID запросов |
| `requireAnalogs` | `true`: отсутствие хотя бы одного аналога считается ошибкой |
| `requireVerifiedTerms` | `true`: неутверждённые условия считаются ошибкой |
| `requireLlm` | `true`: отсутствие настроек LLM считается ошибкой |

Остальные переменные служебные: снимок корзины, состояние подтверждения и диалога.
При смене товара очистите `quantity` и `analogProductId`, если хотите автоматический выбор.
После запуска Postman может сохранить полученный токен в переменных. Не публикуйте
экспорт с заполненными `sessionId` и `chatSessionId`; исходный JSON содержит пустые значения.

## Последовательность и ожидаемый результат

| Шаг | Реальный запрос | Что проверяется |
|---|---|---|
| 01 | `GET /api/health` | 200, приложение работает |
| 02 | `GET /actuator/health` | 200, `UP`, включая настроенный DataSource health indicator |
| 03 | `GET /api/catalog/products?page=0&size=100` | Чтение непустого каталога из PostgreSQL |
| 04 | `GET /api/catalog/products/{productId}` | Сохранённая карточка и исходный артикул |
| 05 | `GET /api/products/search?q={articleEncoded}&page=0&size=20` | Товар найден; точный артикул первым |
| 06 | `GET /api/products/{productId}` | Свежие цена, остаток и допустимое количество |
| 07 | `GET /api/products/{analogProductId}/analogs` | Контракт ответа; объяснение и совпавшие характеристики каждого кандидата |
| 08 | `POST /api/session` без тела | Bearer-токен и срок действия |
| 09 | `GET /api/cart` | Новая корзина пуста |
| 10 | `POST /api/cart/proposals` | Предложение `PENDING` с выбранными товаром и количеством |
| 11 | `GET /api/cart` | После предложения корзина всё ещё пуста |
| 12 | `POST /api/cart/proposals/{proposalId}/confirm` | Товар появляется ровно в выбранном количестве |
| 13 | Тот же запрос подтверждения | Состав, количество и цена совпадают с первым подтверждением |
| 14 | `GET /api/products/{productId}` | Получение актуального остатка для отрицательного теста |
| 15 | `POST /api/cart/proposals` с количеством сверх остатка | 409 и именно `INSUFFICIENT_STOCK` |
| 16 | `GET /api/cart` | Отказ не изменил корзину; `LOCAL_DEMO`, `stockReserved=false` |
| 17 | `GET /api/purchase-terms` | Контракт условий и наличие утверждённого источника, когда он настроен |
| 18 | `POST /api/chat` | Вопрос о карточке по ID, текст и соответствующий `data.id` |
| 19 | `POST /api/chat` | Вопрос «об этом же товаре» без ID, та же сессия и тот же `data.id` |

Детали Actuator скрыты настройкой `show-details=never`, поэтому коллекция не
ожидает отсутствующее поле `components.db`. Проверка `UP` дополняется реальным
чтением товаров из БД на шаге 03.

Тело предложения: `{"requestId":"UUID","productId":123,"quantity":1}`.
Тело подтверждения: `{"revision":1}` — используется фактически полученная ревизия.
Тело чата: `{"messageId":"UUID","text":"Вопрос"}`.
Все значения в JSON коллекции подставляются из переменных.

Если между предложением и подтверждением изменились цена или остаток, сервер
вернёт `requiresConfirmation=true`. Runner остановится на шаге 12 с пояснением.
Проверьте новые условия в ответе. При согласии повторите шаг 12 с сохранённой новой
ревизией, затем выполните шаги 13–19 в той же сессии. Новая ревизия автоматически
не подтверждается. Не начинайте с шага 01 при таком продолжении: он сбрасывает сессию.

## Ограничения и необходимые настройки

- **Реальный диалог с LLM:** проверен после настройки локального backend. На новой установке без `LLM_API_KEY` и `LLM_MODEL` шаги 18–19 получают
  503 с `LLM_NOT_CONFIGURED`. Проверка явной ошибки проходит, но два положительных
  сценария помечены **Skipped**. После настройки backend включите `requireLlm=true`.
- **Утверждённые условия:** пока `PURCHASE_TERMS_FILE` не указывает на файл,
  утверждённый партнёром, API возвращает `verified=false`. Проверка утверждённых
  условий помечена **Skipped**. После настройки источника включите
  `requireVerifiedTerms=true`. Шаблон файла сам по себе не является утверждением.
- **Положительный подбор аналогов:** в текущем прогоне для выбранного товара
  кандидатов не было. Контракт пустого ответа проверен, наличие аналогов — **Skipped**.
  Выберите `analogProductId` с полными согласованными характеристиками и импортированными
  совместимыми кандидатами, затем включите `requireAnalogs=true`.

Другие ошибки, включая недоступность EKT, неверные доступы и ошибки модели,
не подменяются ожидаемым отсутствием настроек и приводят к падению проверок.

## Запуск из терминала

Необязательный вариант через Newman; команды из корня репозитория:

```bash
npx --yes newman@6.2.2 run backend/postman/EKT-Backend.postman_collection.json \
  --env-var baseUrl=http://localhost:8080 \
  --timeout-request 45000 --delay-request 250
```

Для обязательной проверки всех положительных сценариев после подготовки данных и настроек:

```bash
npx --yes newman@6.2.2 run backend/postman/EKT-Backend.postman_collection.json \
  --env-var baseUrl=http://localhost:8080 \
  --env-var requireLlm=true --env-var requireVerifiedTerms=true \
  --env-var requireAnalogs=true --timeout-request 45000 --delay-request 250
```

Newman возвращает ненулевой код при проваленных проверках. Первый запуск `npx`
требует интернета. Зависимости frontend/backend не изменяются.

## Проверенный прогон

23 сентября 2026: локальный backend, PostgreSQL и реальный EKT API, Newman 6.2.2.
Выполнено 19 запросов; 47 проверок объявлено, из них 43 прошли и 4 пропущены,
ошибок нет. Автоматически выбран товар `58379`, артикул `030300435_`.
Пропуски: один положительный подбор аналогов, утверждённые условия, два ответа LLM.
Это результат конкретного прогона; цены, остатки и доступность внешних сервисов могут измениться.

Повторный прогон 23 сентября 2026 после настройки LLM, с `requireLlm=true`: 19 запросов,
49 проверок (47 прошли, 2 пропущены), ошибок нет. Оба запроса чата вернули 200;
продолжение диалога без повторного ID сохранило контекст товара. Оставшиеся пропуски:
положительный подбор аналогов и утверждённые условия. Секреты находятся только
в локальном `.env`, исключённом из Git.
