# EKT backend

Подготовлена основа приложения: Spring Boot 3.5.6, Java 21, Maven Wrapper,
PostgreSQL, Flyway, JPA, Validation и REST-ошибки в формате ProblemDetail.
Существующие `/api/items` и `/api/predict` сохранены. Добавлено чтение каталога
через EKT API и управляемый импорт в PostgreSQL. Добавлены поиск, сессии, локальная корзина, подбор кандидатов-аналогов и API чата; внешние
запросы выполняются при обращении к endpoints товаров, а не при старте.

## Совместимость

Существующая версия Spring Boot 3.5.6 сохранена. Ветка 3.5 поддерживает Java 21
и Maven 3.6.3+ ([официальная документация](https://docs.spring.io/spring-boot/3.5/system-requirements.html)).
Версии Flyway, PostgreSQL JDBC, JUnit, Mockito и Testcontainers управляются Spring Boot BOM.
Wrapper использует Maven 3.9.11; первый запуск требует интернета.

## PostgreSQL в Docker, Spring Boot в IDE

Нужны JDK 21 и запущенный Docker с Compose. Контейнер содержит только PostgreSQL 16.
Команды выполняются из корня репозитория, где находится `docker-compose.yml`:

```bash
# Если .env уже существует, отредактируйте его, не перезаписывайте.
cp .env.example .env
# Задайте свои DB_USERNAME и DB_PASSWORD в .env.
docker compose up -d --wait db
docker compose ps db
```

На Windows файл можно скопировать через `Copy-Item .env.example .env` в PowerShell.
Compose завершит ожидание, когда PostgreSQL пройдёт healthcheck.
База называется `hackdb`, порт доступен только локально: `127.0.0.1:5432`.
Пользователь и пароль берутся из окружения или корневого `.env`.
Значения переменных, уже экспортированных в терминале, имеют приоритет над `.env`.

### Настройка IDE

1. Импортируйте `backend/pom.xml` как Maven-проект и выберите JDK 21.
2. Создайте Java/Spring Boot конфигурацию запуска для
   `com.powerpuff.backend.BackendApplication`, модуль `backend`.
3. В Environment variables задайте значения из вашего `.env`:
   - `DB_URL=jdbc:postgresql://localhost:5432/hackdb`
   - `DB_USERNAME` — тот же пользователь, что у контейнера.
   - `DB_PASSWORD` — тот же пароль, что у контейнера.
4. Запустите основной класс через Run/Debug. Profile `postgres` не требуется:
   PostgreSQL используется по умолчанию.

В IntelliJ IDEA переменные задаются в Run → Edit Configurations → Environment variables.
В VS Code используйте переменные `env` локальной Java launch-конфигурации
или загрузку `.env`, если она настроена вашим расширением. Не коммитьте секреты.

Docker Compose автоматически читает `.env`, Spring Boot — нет. Экспорт переменных
в терминале не меняет окружение IDE, которая была открыта раньше.
Для запуска без EKT оставьте `EKT_ENABLED=false`; endpoints товаров вернут 503.
Для реального каталога задайте в IDE `EKT_ENABLED=true`, `EKT_USERNAME` и
`EKT_PASSWORD` из локального `.env`, затем перезапустите приложение.

### Управление базой

```bash
docker compose logs --tail=50 db
docker compose stop db
docker compose up -d --wait db
```

Данные сохраняются в named volume `pgdata`, в том числе после `docker compose down`.
Не используйте `down -v`, если данные нужны: этот флаг удаляет volume.
Если порт 5432 занят, освободите его или задайте свободный `DB_PORT` в `.env`
и соответствующий порт в `DB_URL` конфигурации IDE.

| Переменная | Значение |
|---|---|
| DB_URL | По умолчанию jdbc:postgresql://localhost:5432/hackdb |
| DB_USERNAME | Обязательный пользователь БД |
| DB_PASSWORD | Обязательный пароль БД |
| EKT_BASE_URL | https://ekt.kz |
| EKT_ENABLED | false; включите для запросов к EKT |
| EKT_USERNAME / EKT_PASSWORD | Не нужны для этапа 1; обязательны при EKT_ENABLED=true |
| CORS_ORIGINS | http://localhost:5173; несколько адресов через запятую |
| PORT | 8080 |

`.env` исключён из Git. Не добавляйте реальные доступы в код или тесты.
Параметр `EKT_ENABLED=true` включает интеграцию и требует настройки доступов.

## Проверка

Для последовательной проверки API импортируйте [Postman-коллекцию](postman/EKT-Backend.postman_collection.json).
[Инструкция запуска и ограничения проверок](postman/README.md) описывают все 19 запросов,
переменные, подтверждение корзины и отдельные проверки LLM и условий покупки.

```bash
curl http://localhost:8080/api/health
curl http://localhost:8080/actuator/health
```

`/api/health` возвращает `{"status":"ok"}` и проверяет HTTP-приложение.
`/actuator/health` дополнительно проверяет подключение к БД, без раскрытия деталей.

Ошибки используют `application/problem+json`: `type`, `title`, `status`, `detail`.
Для ошибок валидации добавляется объект `errors` с именами полей.
В ответах нет stack trace, исходного невалидного JSON или внутренних сообщений исключений.

## Схема и код

- `controller`, `service`, `repository`, `dto`: существующие слои API.
- `entity/Product`: базовые поля будущего каталога.
- `client`: EktClient и отдельные DTO внешнего API.
- `config`: CORS и проверяемая конфигурация EKT.
- `exception`: единая обработка ошибок.
- `db/migration/V1__initial_schema.sql`: таблицы `items` и `products`.

ID товара — Long, назначается EKT. Цена и количество — BigDecimal,
в БД NUMERIC(38,10). Артикул и штрихкод — строки без удаления `_` и ведущих нулей.
Неизвестные цена и количество допускают NULL. REST API возвращает полную карточку, включая properties/offers и склады.
Режим catalog-sync сохраняет эти поля и остатки по складам в PostgreSQL.

Flyway создаёт схему; Hibernate использует `ddl-auto=validate` и не изменяет её.
Для новой установки нужна пустая БД. Если старый Docker volume уже содержит
таблицы от Hibernate, не удаляйте его: используйте отдельную пустую БД либо
согласуйте миграцию существующей схемы. Автоматический baseline не включён.
Изменение пароля в .env не меняет пароль уже созданного пользователя PostgreSQL.

## Тесты

Из backend:

```bash
./mvnw test
```

Быстрые тесты запускают Flyway и JPA validation на H2 (только test scope).
Проверяют health, формат ошибок и сохранение идентификаторов/дробных значений.
Это не заменяет проверку PostgreSQL.

С работающим Docker:

```bash
./mvnw -DpostgresTests=true test
```

Дополнительно запускается PostgreSQL 16 через Testcontainers для проверки
миграции и Hibernate. Без флага этот тест явно пропускается; с флагом и
недоступным Docker тест завершится ошибкой.

## EKT API — этап 2

```bash
curl 'http://localhost:8080/api/products?page=2'
curl http://localhost:8080/api/products/515291
```

Список: `{ "page": 2, "perPage": 20, "count": 20, "items": [...] }`.
Нумерация страниц пока начинается с **1**, как в EKT. `count` — количество
элементов этой страницы; общее количество товаров неизвестно. Пустая страница
возвращается с пустым `items`. Полный обход выполняет отдельный режим catalog-sync, описанный ниже.

Карточка возвращает `id`, `name`, `article`, `description`, `price`, `quantity`,
`stores`, `image`, `url`, `offers`, `properties`. Неизвестные цена/остаток остаются
`null`, массивы и разные типы свойств сохраняются. Список не обогащается деталями
отдельными запросами: остатки обычно доступны только через карточку.
Эти endpoints приходят напрямую из EKT, без записи в БД и без подмены тестовыми данными;
импорт запускается отдельно.
Противоречия исходных характеристик передаются как есть: например, у 515291
название содержит 160 А, а свойство NOMINALNYY_TOK — 250 А. Это не проверка совместимости.

Ошибки содержат стабильное поле `code`:

| HTTP | code | Значение |
|---|---|---|
| 400 | — | Некорректные page/id |
| 404 | PRODUCT_NOT_FOUND | EKT вернул 404 для карточки |
| 503 | EKT_DISABLED | Интеграция выключена |
| 503 | EKT_RATE_LIMITED | EKT вернул 429; повторите позже |
| 502 | EKT_AUTH_ERROR | EKT вернул 401/403 |
| 502 | EKT_HTTP_ERROR | Прочая ошибка HTTP или перенаправление |
| 502 | EKT_UNAVAILABLE | Повторная 502/503/504 от EKT |
| 502 | EKT_CONNECTION_ERROR | Сбой соединения |
| 502 | EKT_INVALID_RESPONSE | Некорректный JSON или структура ответа |
| 504 | EKT_TIMEOUT | Истёк таймаут |

Максимум две попытки GET с паузой 250 мс при сетевой ошибке или 502/503/504.
401/403, 404, 429, остальные статусы и некорректный JSON не повторяются.
Таймаут соединения 5 секунд, чтения — 15 секунд на попытку.
Перенаправления отключены; Basic Auth отправляется только на настроенный EKT origin.
Тела ошибок EKT и учётные данные не передаются клиенту и не пишутся в логи.

Проверка на реальном API: 515291 вернул цену 64920 и quantity 23;
страница 2 вернула 20 товаров. Значения могут измениться.
Клиентские тесты используют синтетические JSON fixtures внутри тестов,
не повреждённый Markdown и не живой API. Команда: `./mvnw test`.

## Импорт каталога — этап 3

Flyway V2 добавляет подробности товара, JSONB `properties`/`offers`, склады,
остатки по паре товар/склад, время обновлений и журнал запусков. Общий остаток
хранится отдельно от складских. Все склады сохраняются как данные источника,
без предположения, что брак, образцы или перемещения доступны для продажи.
Артикул поставщика, бренд и штрихкод извлекаются из properties без изменения исходного JSON.

Запускайте импорт отдельным процессом с профилем `catalog-sync`:
он не занимает порт 8080 и завершает работу после загрузки. Обычный backend
из IDE может работать параллельно. Публичного endpoint запуска импорта нет.

Из корня репозитория, в bash/zsh:

```bash
set -a
source .env
set +a
cd backend
# JAVA_HOME должен указывать на JDK 21.
./mvnw spring-boot:run -Dspring-boot.run.jvmArguments="-Dspring.devtools.restart.enabled=false" -Dspring-boot.run.profiles=catalog-sync
```

По умолчанию это пробная загрузка: **1 страница и максимум 20 деталей**,
пауза 250 мс между запросами. Повтор команды продолжает последний незавершённый
запуск: следующая страница и недостающие/ошибочные детали.

Для полного обхода с защитными пределами:

```bash
./mvnw spring-boot:run -Dspring-boot.run.jvmArguments="-Dspring.devtools.restart.enabled=false" -Dspring-boot.run.profiles=catalog-sync \
  -Dspring-boot.run.arguments="--catalog.sync.max-pages=10000 --catalog.sync.max-details=1000000"
```

Это пределы на запуск, а не известный размер каталога. Полная выгрузка может быть
длительной. Если сработал предел, повторите команду для продолжения. Параметр
`--catalog.sync.resume=false` начинает новое обновление с первой страницы и повторно
загружает детали; товары обновляются по EKT ID, дубликаты не создаются.
Для повторения только неудачных деталей после завершённого обхода страниц
достаточно обычного resume. `--catalog.sync.max-details=0` загружает только список.

В IDE создайте отдельную конфигурацию с профилем `catalog-sync`, теми же DB_*/EKT_*
переменными и аргументами `--catalog.sync.max-pages=... --catalog.sync.max-details=...`.
Основную конфигурацию сервера оставьте без этого профиля.

### Статус

```bash
curl http://localhost:8080/api/catalog/status
```

Ответ показывает `totalProducts`, `productsWithDetails` и последний `run`:
`status`, `reason`, `next_page`, `list_complete`, `products`, `detailsComplete`,
`errors`, время запуска и последнего изменения. Статус `COMPLETE` означает пустую
последнюю страницу и успешные детали всех товаров текущего запуска.
`STOPPED/PAGE_LIMIT` после пробной загрузки — ожидаемый результат, не полный каталог.
`DETAILS_PENDING` означает, что остались детали; ошибки доступны по `error` в
`catalog_sync_products` и `detail_error` в `products`.

Условия остановки: пустая страница завершает список, повтор набора ID останавливает
запуск с `REPEATED_PAGE`, ошибка EKT — с `FAILED` и безопасным кодом причины.
401/403, 429 и недоступность API останавливают поток запросов; ошибка отдельной
карточки 404/некорректный ответ записывается, остальные карточки продолжаются.

Курсор страницы обновляется в одной транзакции с сохранением страницы. Запись
карточки и её складов также атомарна. Сетевых запросов в транзакциях нет.
Advisory lock PostgreSQL запрещает одновременный импорт, в том числе из другой JVM.
После аварийного завершения JVM lock освобождается; запись может остаться RUNNING
до следующего запуска resume. Это сохранённое состояние, а не индикатор живого процесса.
Старые товары не удаляются даже при полном обходе: API не гарантирует стабильный
снимок во время пагинации. Свежесть списка и деталей хранится отдельно.

Повторное чтение краткой карточки не стирает описание, свойства и склады.
При неудачном обновлении деталей старые данные остаются с прежним временем обновления
и кодом ошибки. Проверку актуального наличия перед покупкой это не заменяет.

Проверки импорта выполняются командой `./mvnw -DpostgresTests=true test` на PostgreSQL 16.

Для повторения деталей без загрузки новых страниц (в том числе после таймаута):

```bash
./mvnw spring-boot:run -Dspring-boot.run.jvmArguments="-Dspring.devtools.restart.enabled=false" \
  -Dspring-boot.run.profiles=catalog-sync \
  -Dspring-boot.run.arguments="--catalog.sync.max-pages=0 --catalog.sync.max-details=20"
```

Для CLI отключайте DevTools через указанный JVM-параметр: это позволяет Maven
возвращать ненулевой код при ошибке импорта. В IDE задайте этот параметр в VM options.
Статус в БД остаётся основным источником полноты загрузки; успешное завершение
ограниченного запуска не означает загрузку всего каталога.

## Поиск по PostgreSQL — этап 4

```bash
curl --get 'http://localhost:8080/api/products/search' \
  --data-urlencode 'q=Legrand' --data-urlencode 'page=0' --data-urlencode 'size=20'
```

Поиск обращается только к PostgreSQL и работает при `EKT_ENABLED=false` и
недоступности EKT. Он охватывает **только уже импортированные товары**.
Полноту импорта проверяйте через `/api/catalog/status`.

Параметры: обязательный `q` (1–200 символов, максимум 10 слов), `page` от 0
до 1000000, `size` от 1 до 100 (по умолчанию 20). Пустой запрос и неверные
параметры возвращают 400. Пробелы по краям удаляются, повторные пробелы объединяются.

Поиск нечувствителен к регистру. Каждое слово должно встретиться хотя бы в одном
из полей: исходный артикул, артикул поставщика, название, бренд. Порядок слов
неважен. Это поиск по подстрокам, без исправления опечаток и семантического поиска.
Символы `_`, `%` и `!` ищутся буквально, ведущие нули сохраняются.

Ранжирование: точный исходный артикул → точный артикул поставщика → полная фраза
в названии → остальные совпадения. Внутри группы сортировка по названию и ID
обеспечивает стабильную пагинацию при неизменном каталоге. Count и items читаются
в одной read-only транзакции REPEATABLE READ. Между отдельными запросами страниц
каталог может обновиться импортом.

Ответ содержит `query`, `page`, `size`, `totalElements`, `totalPages`, `items`.
Для пустой выдачи — `items: []`, `totalElements: 0`, `totalPages: 0`.
На странице за пределами выдачи items пустой, общее количество остаётся реальным.
В каждом item: ID, название, оба артикула, бренд, цена, общий остаток, ссылки,
`listUpdatedAt`, `detailUpdatedAt`, `detailError`. Неизвестные значения — null.
Остаток актуален на момент загрузки деталей, цена — последнего обновления карточки.
Перед покупкой необходима повторная проверка EKT.

Существующие `/api/products?page=1` и `/api/products/{id}` продолжают читать EKT
напрямую. Их нумерация страниц начинается с 1; нумерация **поиска** — с 0.

Для текущего прототипа используется параметризованный SQL по подстрокам.
Производительность на полном каталоге ещё не измерялась; при росте объёма нужно
проверить план запросов и при необходимости добавить специализированные индексы.

## Консультации, корзина и чат

Полный контракт с примерами: [docs/frontend-api.md](docs/frontend-api.md).

Дополнительные настройки окружения IDE:

- `FRONTEND_BASE_URL` — origin фронтенда для ссылки /cart.
- `LLM_API_KEY`, `LLM_MODEL` — доступ и модель OpenAI с function calling в Responses API.
- `PURCHASE_TERMS_FILE` — абсолютный путь к утверждённому JSON с условиями.
  Пример: [purchase-terms.example.json](docs/purchase-terms.example.json).
  После проверки партнёром укажите source и verified=true; не используйте выдуманные условия.

Реализация LLM следует [официальному контракту function calling](https://developers.openai.com/api/docs/guides/function-calling).
Одна модель выбирает действие; фактический ответ собирается сервером из результатов сервисов.
Это ограниченный консультант, а не агент с произвольными инструментами.
Для неопределённых запросов предусмотрено уточнение. Без ключа нет симуляции LLM.

Корзина использует сессии с 24-часовым сроком и 10-минутные предложения.
Все изменения сериализуются блокировкой сессии в БД. Повторное подтверждение
идемпотентно, EKT проверяется перед транзакцией, сумма количества с уже добавленным
не превышает полученный остаток. Изменённая цена/остаток требуют новой ревизии
подтверждения. Данные поставщика могут измениться после проверки: локальная
корзина не является резервом или заказом EKT.

Подбор аналогов пока ограничен автоматическими выключателями с полным набором
параметров. Требуется точное совпадение типа, полюсов, напряжения, тока,
отключающей способности и установки. Противоречивые данные исключаются.
Результат — кандидат для проверки специалистом, не гарантия взаимозаменяемости.
Без подходящих данных возвращается пустой список с причиной.

### Готовность к демо

- Запуск, PostgreSQL, Flyway, импорт, поиск, чтение сохранённых и свежих карточек — реализованы.
