# Проверка backend EKT: характеристики, аналоги и импорт

Состояние работ на 23 сентября 2026. Секреты и выбранная модель LLM не менялись.
Ни заказов, ни резервов EKT не создавалось. Ниже разделены реализованное поведение,
проверки на тестовых данных и ограничения реального каталога.

## Конфликт характеристик

Одинаковая диагностика применяется к свежей и сохранённой карточке. Она сравнивает
значения тока из `name`, `description` и `properties.NOMINALNYY_TOK`.
Учитываются кириллические/латинские А, регистр, десятичная запятая, обычные и
неразрывные пробелы. Значение свойства переводится в амперы для сравнения;
например, `0,160 кА` эквивалентно `160 А`. Значения кА/мА в свободном описании
не смешиваются с номинальным током: обычно это отключающая способность или утечка.
Диапазоны серии («от 6 до 63А», «6–63А») не считаются номиналом конкретного товара.

Это консервативная проверка расхождений, а не извлечение всех электрических
характеристик из произвольного текста. Неоднозначное описание требует проверки
специалистом; алгоритм не выбирает правильную сторону конфликта.

Карточка `515291` возвращает конфликт 160/250 А. Исходные `name`, `description`
и `properties` не изменены. В `characteristicConflicts[].evidence` находятся
`source`, `rawValue`, `normalizedValue`, `unit`; текстовое предупреждение — в
`product.warnings` сохранённой карточки или `warnings` свежей карточки.
Существующий массив кодов `StoredProductResponse.warnings` сохранён.
Основной `text` ответа чата также содержит предупреждение и предлагает уточнение.

## Правила подбора

Поддержана только предварительная группа «Автоматический выключатель» по
`properties.OBYEM`. Требуется совпадение всех семи непустых свойств:

1. `OBYEM` — тип.
2. `KOLICHESTVO_POLYUSOV` — полюса.
3. `NOMINALNOE_NAPRYAZHENIE` — напряжение.
4. `NOMINALNYY_TOK` — номинальный ток.
5. `NOMINALNAYA_OTKLYUCHAYUSHCHAYA_SPOSOBNOST` — отключающая способность.
6. `TIP_USTANOVKI` — крепление.
7. `KHARAKTERISTIKA_SRABATYVANIYA` — характеристика срабатывания.

Сравнение свойств пока строковое без учёта регистра. Нормализация единиц в
диагностике конфликта не означает, что нормализованный подбор всех параметров
уже реализован. Разные обозначения одного параметра могут давать пустую выдачу.
Незаполненные поля, типичные заглушки «неизвестно»/«нет» и выявленные конфликты
исключают источник из подбора. Кандидат должен иметь загруженную карточку без
ошибок обновления и предупреждений, положительный сохранённый остаток и все
совпадающие поля. Название и `RECOMMEND` не используются как доказательство.

**Подтверждено реализацией и тестами:** эти ограничения действительно применяются;
неполные и конфликтные данные не дают подтверждённую совместимость.
**Предварительно, не утверждено партнёром:** выбор семи полей и сама область
категории. Нужны правила габаритов, расцепителя, применения и других критичных
параметров. Семь совпадений не доказывают полную взаимозаменяемость.

Поэтому API явно возвращает `confirmed:false`, а элементы выдачи имеют
`compatibilityStatus:"UNCONFIRMED_CANDIDATE"`. Ни одна такая карточка не должна
показываться пользователю как подтверждённый аналог. Нет реального положительного
примера подтверждённой замены; тест с двумя согласованными карточками проверяет
только предварительного кандидата и использует **синтетические fixtures** в
отдельной тестовой PostgreSQL, не в рабочем каталоге.

## Реальный пример отсутствия товара

`21182`, артикул `310100024_`: нулевой остаток. Похожий `33703`, артикул
`010400569_`: положительный остаток при проверке. Совпадают полюса, ток,
напряжение и характеристика C, но отключающая способность различается
(`4,5кА` / `20кА`), у исходного товара не заполнено крепление и нет обязательного
`OBYEM`. Это **не подтверждённый аналог**.

API и основной текст чата говорят: товар отсутствует по данным синхронизации,
подтверждённых аналогов не найдено, подбор следует уточнить у менеджера.
Передача запроса менеджеру не заявляется и не выполняется.
Прямое предложение добавить отсутствующий товар отклоняется с
`409 INSUFFICIENT_STOCK`; корзина не меняется.

## Полный импорт

Последовательно получены страницы 1–752: **15 037 уникальных ID** сохранены в БД.
Страница 752 содержит 17 записей; 753 и страницы далеко за границей возвращают
первую страницу. [Доказательство поведения пагинации](demo/pagination-evidence.json).
Поле `count` относится к странице; не используется как размер каталога.

По умолчанию повтор страницы останавливает импорт с `REPEATED_PAGE`. Для
наблюдаемого поведения EKT добавлен явный флаг `catalog.sync.accept-short-page-wrap`.
Только при включённом флаге, повторе именно сохранённой первой страницы после
страницы с номером больше 1, повторной проверке предыдущей непустой короткой
страницы и совпадении её ID с сохранённым отпечатком конец списка принимается.
В БД сохраняется `end_condition=WRAP_AFTER_VERIFIED_SHORT_PAGE`.
Другие повторы не объявляются концом каталога. Пустой ответ также поддерживается
и записывает `end_condition=EMPTY_PAGE`.

Обход списка завершён. Загрузка подробных карточек выполняется отдельно в том
же процессе и **на момент подготовки отчёта ещё идёт**. Завершение списка не равно
завершению всего импорта. Проверяйте `GET /api/catalog/status`:

- `totalProducts` — уникальные товары в БД;
- `productsWithDetails` — товары, у которых когда-либо успешно загружены детали;
- `run.products` — уникальные ID текущего обхода;
- `run.detailsComplete`, `detailsPending`, `errors` — состояние подробных карточек;
- `run.list_complete`, `end_condition` — наблюдаемый конец списка;
- `run.complete` — весь запуск завершён, очередь пуста; до этого `false`.

Запущена последовательная загрузка, без параллельных запросов, с паузой 250 мс
между запросами. Большой каталог требует длительного выполнения. Таймаут
подключения 5 с, чтения 15 с; максимум две попытки для сетевых ошибок и HTTP
500/502/503/504. 429 останавливает импорт, чтобы не усиливать ограничение EKT;
после восстановления доступности продолжите тот же запуск. Ошибки авторизации
и невалидный JSON бесконечно не повторяются.

Возобновление после сбоя (в отдельном процессе, с окружением `.env`, уже переданным
приложению; Spring Boot сам `.env` не читает):

```bash
cd backend
./mvnw spring-boot:run \
  -Dspring-boot.run.jvmArguments=-Dspring.devtools.restart.enabled=false \
  -Dspring-boot.run.profiles=catalog-sync \
  '-Dspring-boot.run.arguments=--catalog.sync.max-pages=100000 --catalog.sync.max-details=1000000 --catalog.sync.delay-ms=250 --catalog.sync.accept-short-page-wrap=true'
```

Обычный `resume=true` продолжает незавершённый запуск и пропускает успешные детали.
Не запускайте второй импорт одновременно: PostgreSQL advisory lock отклонит его.
Повторное обновление по ID не создаёт дубликаты. Ошибка запроса сохраняет прежний
остаток и выставляет `DETAIL_REFRESH_FAILED`. Если успешная карточка не содержит
остатка, он становится неизвестным (`null`), а не нулевым. Такой товар нельзя
добавить в корзину. Нулевой остаток принимается только как реальное значение.
Каталог поставщика может меняться во время обхода; API не предоставляет snapshot token.

## Условия, склады и вопросы партнёру

`PURCHASE_TERMS_FILE` поддерживает загрузку утверждённого JSON. Требуются
`verified:true`, непустой `source` и непустые `payment`, `delivery`, `minimumOrder`.
Техническая валидация файла не доказывает, что документ действительно утверждён:
это должен подтвердить партнёр. Реальный файл пока не предоставлен;
`GET /api/purchase-terms` возвращает `verified:false` и «Не уточнено».

Нужно получить конкретные ответы EKT:

1. Какие ID складов доступны для продажи и отгрузки? Как исключать брак, витрины,
   перемещения, образцы и маркетинговые склады?
2. `quantity` — физический, свободный или доступный к продаже остаток? Как он связан
   с суммой `stores[].quantity`?
3. Вычтены ли резервы? Как использовать `KOLICHESTVOVREZERVE` и насколько актуальны данные?
4. В какой валюте возвращается `price`, включены ли налоги?
5. В каких единицах измеряется количество каждого товара: штуки, метры, упаковки?
6. Как различаются минимальная партия и кратность? Является ли `KRATNOST_MIN`
   одновременно минимумом и шагом, как трактовать остальные поля кратности?
7. Где утверждённые условия оплаты, доставки и минимального заказа, кто их согласует?
8. Подтверждается ли наблюдаемое поведение конца пагинации и есть ли стабильный
   snapshot/общее число товаров для проверки полноты выгрузки?

Backend не суммирует все склады как доступные для покупки. `quantity` отображается
как значение поставщика; `stockStatus=REPORTED_STOCK_NOT_CONFIRMED_SELLABLE` и
`cart.availabilityConfirmed=false` явно обозначают, что отгрузка не подтверждена.
Существующая локальная корзина по-прежнему ограничивает количество значением EKT,
но это демонстрационная проверка, а не утверждение о доступности склада, резерв или заказ.

## Сертификаты, вложения и оставшиеся ограничения

В проверенной исходной карточке EKT доступны стандартные поля, отдельных верхних
полей сертификата нет. Среди уже импортированных свойств на момент проверки поля
сертификатов не обнаружены. Все исходные свойства сохраняются; если ключ содержит
`certif`, `sertif` или `сертиф`, его точное содержимое дополнительно возвращается
в `certificateSources` с исходным путём. URL, массив или ID не подменяются придуманным
документом. Это извлечение сведений, а не проверка юридической действительности
сертификата. Отдельный документ по ID без известного API скачивания не разрешается
в выдуманную ссылку. Новые схемы/верхние поля требуют контракта партнёра.

Обработка PDF/Excel/Word/фото-вложений не реализована: `/api/chat` принимает текст.
Казахский язык, сопутствующие рекомендации, история авторизованных пользователей
и эскалация менеджеру остаются опциональными пробелами. Текущая история привязана
к временной сессии, не к авторизованному аккаунту. Локальная корзина не является
корзиной ekt.kz. Эти части не расширялись.

## Проверки

JUnit/Mockito и настоящая тестовая PostgreSQL проверяют конфликт, Unicode/единицы,
диапазоны серии, сохранение свидетельств и сертификата из fixture, неизвестные
остатки, повторы/возобновление импорта, подтверждение без дублей, изменение условий,
изолированные сессии и HTTP-ответ предварительного кандидата.

Обновлённая [основная Postman-коллекция](../postman/EKT-Backend.postman_collection.json)
содержит 22 запроса; [демо отсутствующего товара](../postman/EKT-Unavailable-Product.postman_collection.json)
проверяет основной текст отказа и исправленный конфликт. Реальные ответы LLM,
карточки EKT и корзина проверяются отдельно от fixtures. Прошедшие тесты не
закрывают подтверждение реального аналога, утверждение условий и весь кейс.
