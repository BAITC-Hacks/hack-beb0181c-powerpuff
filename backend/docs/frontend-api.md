# Контракт backend для фронтенда

Обновление 23.09.2026: [правила, прогресс импорта и ограничения](backend-hardening.md).
Прежние маршруты и тела запросов сохранены. Добавлены поля ответа:

- В карточке товара: `characteristicConflicts: [{code, parameter, message, evidence: [{source, rawValue, normalizedValue, unit}]}]`,
  `warnings: string[]` с понятным текстом, `certificateSources: {"properties.KEY": <исходный JSON>}`,
  `stockStatus: "UNKNOWN" | "OUT_OF_STOCK" | "REPORTED_STOCK_NOT_CONFIRMED_SELLABLE"`.
  Для сохранённой карточки это поля внутри `product`; внешний `warnings` по-прежнему содержит коды.
- В ответе аналогов: `confirmed:false`; у каждого элемента `compatibilityStatus:"UNCONFIRMED_CANDIDATE"`.
  Совпадение семи свойств даёт предварительного кандидата, не подтверждённую замену.
- В корзине: `availabilityConfirmed:false` — доступность отгрузки не подтверждена партнёром.
- В `run` статуса импорта: `detailsPending`, `complete`, `end_condition`.

Показывайте предупреждения карточки и основной `text` чата. Исходные конфликтующие
значения сохраняются; не выбирайте одно автоматически. Причина отсутствия аналогов
теперь есть и в `message` результата подбора, и в основном `text` ответа чата.

Backend: `http://localhost:8080`. Все тела — JSON. CORS_ORIGINS должен содержать адрес фронтенда.
Ошибки: ProblemDetail `{status, detail, code?}`; ошибки валидации дополнительно содержат `errors`.

## Каталог

- `GET /api/products/search?q=Legrand&page=0&size=20` — поиск в PostgreSQL, size ≤ 100.
- `GET /api/catalog/products?page=0&size=20` — список из PostgreSQL.
- `GET /api/catalog/products/{id}` — сохранённая карточка: `{product, listUpdatedAt, detailUpdatedAt, detailError, warnings}`.
- `GET /api/products/{id}` — свежая карточка EKT.
- `GET /api/products?page=1` — страница из EKT (здесь page начинается с 1).
- `GET /api/catalog/status` — полнота и статус импорта.
- `GET /api/products/{id}/analogs` — кандидаты с объяснением и ограничениями.
- `GET /api/purchase-terms` — условия; `verified:false` означает, что источник пока не предоставлен.

В каталоге нет подтверждённого поля сертификата. Ссылки и исходные свойства передаются
как есть; не показывайте придуманные сертификаты. Конфликт токов в карточке отмечается
`NOMINAL_CURRENT_CONFLICT`. Алгоритм аналогов пропускает такие карточки.

## Сессия

`POST /api/session` без тела:

```json
{"token":"<непрогнозируемый токен>","tokenType":"Bearer","expiresAt":"..."}
```

Передавайте `Authorization: Bearer <token>` для корзины и чата.
Токен действует 24 часа. На сервере хранится только его хеш.
После истечения сессии данные удаляются фоновым заданием в течение 5 минут.
При 401 создайте новую сессию. Не помещайте токен в URL.

## Корзина

Все маршруты требуют действующую сессию; productId не даёт доступа к чужой корзине.
`GET /api/cart` возвращает согласованный снимок из PostgreSQL:

```json
{
  "version": 4,
  "items": [{"productId": 515291, "name": "Название из EKT", "article": "200300285_",
    "image": "https://ekt.kz/...", "quantity": 3, "price": 64920, "subtotal": 194760, "orderMultiple": 1}],
  "total": 194760,
  "cartUrl": "http://localhost:5174/cart",
  "mode": "LOCAL_DEMO", "stockReserved": false, "availabilityConfirmed": false
}
```

Числа в примере иллюстрируют формат, а не текущую цену. `image`, `article` и
`orderMultiple` могут быть null. Нет подтверждённых валюты и единиц.
`orderMultiple` берётся из сохранённого KRATNOST_MIN; неизвестный шаг не угадывается
по названию. Подробную карточку открывайте через `GET /api/products/{productId}`.
`cartUrl` строится из FRONTEND_BASE_URL и ведёт на реализованную страницу `/cart`.
Корзина не резервирует товар и не создаёт заказ или корзину на ekt.kz.

### Добавление — прежний контракт

`POST /api/cart/proposals`:

```json
{"requestId":"<UUID запроса>","productId":515291,"quantity":1}
```

Ответ — предложение `{id, productId, name, quantity, price, stock, revision, status,
expiresAt, operation:"ADD", cartVersion}`. Для ADD quantity — количество, которое
нужно добавить. Создание предложения не меняет корзину. Новый запрос отменяет
предыдущее неподтверждённое предложение сессии. Повтор requestId с теми же данными
возвращает прежнее предложение; с другими — `409 REQUEST_ID_REUSED`.

`POST /api/cart/proposals/{id}/confirm` с `{"revision":1}`:
ответ `{added, requiresConfirmation, proposal, cart}`. При `requiresConfirmation:true`
корзина не меняется: покажите новые цену/остаток и дождитесь отдельного подтверждения
с новой revision. Срок предложения — 10 минут. Повтор уже успешного подтверждения
ничего не добавляет и возвращает текущую корзину (added означает, что это предложение
уже выполнено, а не новую мутацию). Миграция V6 отменяет старые PENDING-предложения
без версии: для них нужно создать новое.

### Изменение количества

`PUT /api/cart/items/{productId}`:

```json
{"requestId":"<UUID операции>","quantity":3,"cartVersion":4}
```

**quantity — целевое количество**, а не прибавка. Значение 2 → 3 даёт ровно 3.
`cartVersion` обязателен и берётся из последнего показанного пользователю снимка.
Кнопка «Применить» является явным подтверждением этого целевого количества.
Сервер проверяет положительность, точность числа и известную кратность.
Ноль отклоняется; удаление выполняется только отдельным DELETE.

Ответ `{updated, requiresConfirmation, proposal, cart}`:

- Обычный успех: `updated:true`, `requiresConfirmation:false`, `proposal:null`,
  новый снимок корзины с пересчитанными subtotal, total и увеличенной version.
- Увеличение запрашивает свежую карточку EKT и проверяет остаток на целевое количество.
  Если цена отличается от сохранённой, возвращается `updated:false`,
  `requiresConfirmation:true` и предложение `operation:"SET"`; корзина остаётся прежней.
  Для SET quantity — целевое количество. Покажите новые условия и подтвердите через
  тот же `/api/cart/proposals/{id}/confirm` только после повторного нажатия пользователя.
  Если цена/остаток снова изменились, понадобится новая revision и ещё одно подтверждение.
- Уменьшение проверяет сохранённую кратность, сохраняет прежнюю цену и не вызывает EKT.
  Если источник кратности непонятен, возвращается UNKNOWN_MULTIPLE; удалить товар можно.

### Удаление

После диалога с названием товара:

```http
DELETE /api/cart/items/515291?requestId=<UUID операции>&cartVersion=4
Authorization: Bearer <token>
```

Тела нет. Ответ — текущая корзина в том же формате, что GET. Для последней позиции
`items:[]`, `total:0`. EKT не вызывается. Повтор того же запроса не удалит заново
добавленный товар: он только возвращает текущий снимок.

### Версии, повторы и параллельные запросы

Любая успешная мутация увеличивает версию корзины и отменяет все PENDING-предложения
этой сессии. Подтверждённое предложение остаётся идемпотентным. Устаревшее ADD или
SET не восстановит удалённый товар и не перезапишет последующее изменение количества.
Сеть выполняется вне транзакции; после ответа EKT версия проверяется повторно под
блокировкой сессии. Чтение снимка, мутация и запись идентификатора операции атомарны.

При неопределённом сетевом результате повторяйте тот же requestId, целевое количество
и исходную cartVersion. Применённая операция не выполняется снова, ответ содержит
актуальную корзину. Другой payload с тем же ID отклоняется. После CART_CHANGED
прочитайте GET /api/cart и получите новое явное подтверждение с новым requestId:
не повторяйте изменение автоматически поверх новой версии.

| HTTP / code | Причина и действие интерфейса |
|---|---|
| 401 SESSION_REQUIRED | Сессия отсутствует/истекла; предложить новую, не повторять мутацию |
| 404 CART_ITEM_NOT_FOUND | Позиции нет в корзине этой сессии; обновить список |
| 409 CART_CHANGED | Устарела версия; обновить корзину и повторно подтвердить выбор |
| 409 PROPOSAL_STALE | Предложение отменено изменением корзины или другим предложением |
| 409 PROPOSAL_CHANGED / PROPOSAL_EXPIRED | Неверная ревизия или истёк срок предложения |
| 409 INSUFFICIENT_STOCK | Целевое количество превышает свежий остаток |
| 409 INVALID_MULTIPLE / UNKNOWN_MULTIPLE | Нарушена или не определена кратность |
| 409 REQUEST_ID_REUSED | Идентификатор использован с другим payload |
| 409 PURCHASE_DATA_UNKNOWN | Свежая цена или остаток неизвестны |
| 400 INVALID_QUANTITY или ошибка валидации | Недопустимое, нулевое или отрицательное количество |

При ошибке сервер не меняет корзину. UI сохраняет подтверждённые данные, показывает
ошибку рядом с позицией и позволяет обновить снимок. Итог берётся из ответа backend.

## Чат

`POST /api/chat`:

```json
{"messageId":"<UUID сообщения>","text":"Найди Legrand"}
```

Ответ: `{messageId, text, data}`. data содержит карточки, предложение, условия
или результат подтверждения. Повторите тот же messageId и text при сетевом сбое;
готовый ответ будет возвращён из БД, без повторения действия.
MESSAGE_IN_PROGRESS — предыдущая обработка того же ID ещё не завершена.
На сессию допускается до 100 сообщений, текст до 4000 символов.

Модель выбирает действие, backend вызывает разрешённый сервис и формирует ответ
из данных. Она не получает инструмент изменения корзины или оформления заказа.
Текстовое подтверждение принимается только как точная фраза «да, добавь» или
«да добавь» для единственного активного предложения. Остальные формулировки
не изменяют корзину. Предпочтительный путь UI — кнопка с id и revision.

Чат требует LLM_API_KEY и LLM_MODEL. Без них — 503 LLM_NOT_CONFIGURED.
Используется OpenAI Responses API, store=false; сохраняется до 5 предыдущих
обменов для контекста в запросе к провайдеру. Внешнее качество модели и задержка
без ключа не проверены. Числовые последовательности, похожие на платёжные номера,
маскируются; не предлагайте вводить платёжные реквизиты в чат.

## Что остаётся внешней настройкой

- Ключ и модель OpenAI в окружении запуска backend.
- Утверждённые условия EKT через PURCHASE_TERMS_FILE.
- FRONTEND_BASE_URL и CORS_ORIGINS для фактического origin frontend.
- Полнота импорта проверяется через /api/catalog/status.
- Правила доступности складов, единицы и валюта требуют подтверждения партнёра.

PDF/Excel/Word/фото-вложения, казахский язык и передача диалога менеджеру пока
не реализованы. Текущий backend принимает текстовые сообщения.
